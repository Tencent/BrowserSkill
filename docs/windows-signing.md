# Windows release signing

CLI releases use three stages:

1. **Release CLI** builds the five targets from a `cli-v<version>` tag. Unix archives are ready to distribute. Windows is uploaded as an unsigned `bsk.exe` plus a signing request, identified by GitHub run ID and run attempt. This workflow has no release write permission.
2. The internal **BK-CI signing pipeline** receives the same tag event, waits for the entire GitHub build to succeed, and checks that the tag belongs to the default branch. It validates the immutable artifact and request, calls the Windows EV signing plugin, checks that executable content has not changed, and uploads the signed file and its provenance to a **draft** GitHub release.
3. **Publish CLI**, triggered by the completed build, waits up to 30 minutes for the matching signature. A Windows runner checks the SHA256, unchanged executable content, trusted Authenticode chain, Tencent publisher and timestamp using PowerShell and `signtool verify /pa /all /v /tw`. Only then does it zip the Windows executable, generate `version.json` from all final archives, and publish the complete release.

The existing Tencent DevOps(OpenSource) check is a separate CodeCC service. It is not the signing pipeline.

## Internal pipeline setup

Import [the BK-CI template](../ci/windows-signing.yml) into the internal project. Fill in the Keystore application ID and the credential generated by binding that application to the BK-CI project. The signing plugin needs that project credential; a separately created AuthID is not a substitute for the project binding.

Create a GitHub release credential of type Access Token in that project. It needs Actions read and Contents write for this repository. A fine-grained token works when organization policy and membership permit it. Outside collaborators may need a classic token with `public_repo` for this public repository; that scope also covers other public repositories the account can access. A dedicated GitHub App is an alternative for long-lived organization credentials. Keep token values in the credential store only, and renew expiring credentials.

Replace `REVIEWED_COMMIT_SHA` with the exact reviewed deployment commit, not a moving branch. The template provides two optional String inputs: `release_tag` and `source_run_id`. They are used for manual recovery; automated tag events supply the tag through `BK_CI_REPO_GITHUB_WEBHOOK_CREATE_REF_NAME`.

Associate `Tencent/BrowserSkill` with the project and grant the standard **Tencent Blueking DevOps** GitHub App access to the repository. After importing the pipeline YAML, use the UI to add a **GitHub event trigger**, choose **Create Branch Or Tag**, and include only `cli-v*`. Publish from the UI. Some internal versions drop CREATE events when converting UI configuration back to YAML; do not switch modes after adding this trigger. Branch creation events are rejected by the signing script even if their name matches.

The Bash plugin resolves the credential expression in its script; the template disables command tracing before exporting it. Step-level credential expressions were not resolved by the tested internal deployment; ordinary input variables are passed as step environment variables. Keep signing credentials confined to the signing step. The GitHub credential is available only to the preparation and return steps. Do not enable pull-request triggers or use failure-continue on any step.

## Release and recovery

Create a CLI release tag using the normal release process. Its version must match `Cargo.toml`, and the commit must be reachable from the repository's default branch. No unsigned Windows package is published while signing is pending or failed.

- **Build failed or artifacts expired:** rerun the **entire** Release CLI run. All platform artifacts must belong to the same run attempt. For manual dispatch, select the release tag as the workflow ref, not `main`.
- **Internal signing failed:** fix the reported cause, then manually run the BK-CI pipeline with the exact `release_tag` and `source_run_id`. An already published version is rejected.
- **Publishing timed out waiting for signing:** once the BK-CI handoff has succeeded, dispatch **Publish CLI** with the successful build's run ID. Do not rebuild merely to retry publication.
- **A source run was rerun:** old handoffs are rejected. Sign the new run attempt and retry Publish CLI.
- **A version is already published:** use a new version/tag. This flow does not replace published release files.

The release becomes visible only after all checks pass. Staging `.exe` and provenance assets are removed before publication; the public Windows download is the signed ZIP and `version.json` contains its final checksum.

## Validation

Run the protocol and manifest tests:

```sh
python3 scripts/windows-release.test.py
node --test scripts/render-version-json.test.mjs
```

The isolated integration test for the existing `cli-v0.3.2` executable passed remote EV signing, executable-content preservation, Windows trust/publisher/timestamp verification, and `bsk --version` execution on a Windows GitHub runner. This is not a test of Windows 11 Smart App Control policy on an end-user device; that acceptance test should be performed with a released signed build.
